# PKR Submission Package — Evidence Confidence Level Explanations (v1.0, Published)

**Published 24 August 2026.** Content approved by the Founder, 23 August 2026; all five records below are Version 1.0. The one open item blocking publication — whether a Definition PKR needs its own Source PKR — is resolved (Founder decision, 24 August 2026): a Definition PKR that translates a Standard's own already-approved definitions, rather than asserting a new evidentiary claim, may cite that Standard directly in its Supporting Source(s) field. All five records now do so, and move to Published on that basis.

**Identifiers migrated the same day**, per KIT OM v0.4 §10.2B: the `EVIDENCE-CONFIDENCE` subject-scope extension proposed at §2 below was itself retired within hours of being confirmed, once the Founder asked whether subject-scope belonged in PKR codes at all. It didn't — for any type, not just these — so these five records now use the same plain sequential format as everything else: `PKR-DEF-000001` through `PKR-DEF-000005`. See §2 for the mapping.

A small open question surfaced while approving these: these records aren't traceable to a Source PKR the way factual PKRs are — their "source" is EAS §5.4 itself, a Standard, not an ARC or Assessed Finding, and the Source PKR mechanism (PKR Standard §5.5) is built around ARC content specifically. Whether Definition PKRs describing Standards-level terminology need a Source PKR at all, or whether citing the Standard directly in this field is sufficient, isn't settled by the existing rules — flagged in Project_Backlog.md rather than assumed either way.

Built per KIT Operations Manual v0.2. This is a different kind of source material than every other PKR built so far: it doesn't trace to a research commission's Assessed Findings, because it isn't a new evidentiary claim. It's a plain-language translation of EAS v1.4 §5.4's existing, already-Founder-approved formal definitions — the kind of work a Definition PKR (PKR Standard §5.6) exists for.

**Why this exists:** the confidence levels (Very High, High, Moderate, Low, Very Low) are already gardener-facing per PKR Standard §4.1, but nothing currently tells Pip what to say if a gardener asks what "Moderate" actually means. Left unspecified, Pip would have to generate that explanation on the spot, in whatever wording occurred to it in the moment — exactly the kind of ungoverned AI-authored wording the Wording Boundary (§4.3/§7.7) exists to prevent, applied here to a case that isn't a factual claim about a rose but is still meaning that shouldn't drift.

## 1. Triage

Not routed from an ARC — routed directly from EAS v1.4 §5.4's formal Evidence Confidence Level definitions, translated into gardener-facing plain language under the Translation Boundary (PKR Standard §4.3): clarify wording only, never change what the formal definition asserts.

## 2. PKR Identifiers — Migrated

These five records were originally submitted with `EVIDENCE-CONFIDENCE` as a proposed subject-scope, since they aren't plant-specific at all — they're system-wide terminology applying to every future plant this platform supports. That question (what does a genuinely non-plant-specific record's ID look like?) is what prompted the Founder to ask whether subject-scope belonged in the ID convention at all — and once asked, the answer applied to every PKR type, not just this one. The convention now used (KIT OM v0.4 §10.2) is `PKR-<TYPE-CODE>-<sequence>`, with no scope segment for anyone:

## 4. What This Doesn't Yet Do

Building these records answers "what should Pip say" — it doesn't yet answer "when does Pip say it." Right now nothing in the Pip Runtime Architecture specifies that a gardener pressing or tapping a shown confidence level should trigger Pip to retrieve and present the matching Definition PKR here, rather than generating an explanation freely. That's an Interface Layer behaviour, not a knowledge-content question, and it belongs in the Pip Runtime Architecture rather than in these records themselves — flagged here, not built, since I haven't reviewed that document this session and shouldn't propose changes to it unread.

## 6. Founder Review Rendering

**What these records are for:** so that when a gardener sees a confidence label next to something Pip tells them and taps it, Pip has one approved, consistent explanation to give — the same one every time, for every plant this platform ever covers — instead of improvising an explanation in the moment.

**What they rest on:** EAS v1.4 §5.4's existing formal definitions, translated for a beginner gardener, not new research or a new evidentiary claim.

**Preserved limitations:** none — these aren't factual claims about a plant, so there's nothing to preserve uncertainty about beyond what's already true of EAS's own definitions.

**Open items:** none remaining. The ID convention extension (§2), the Source PKR question, and the interface-behaviour wiring (§4) were each flagged rather than decided at submission time — all three are now resolved per §5 above.
