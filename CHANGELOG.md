# AskPIP Core Changelog

This changelog records significant changes to AskPIP Core in a concise, human-readable form.

Git provides the complete technical history of the repository. This changelog records the major documents, decisions, releases and structural changes that are important to the Founders and future contributors.

---

## Unreleased

### Changed

- Garden Shed notice panel's Save and Request Review buttons moved up to sit directly under the Approved checkbox (10 September 2026), asked directly: they previously sat below the Notes textarea, so saving a plain approve/unapprove — the common case, with nothing to write — always meant scrolling past Notes first. Notes now follows the buttons instead, there whenever there's something to add rather than sitting in the way every time; its "Request Review" hint text, which used to say "raised in the notes above," was updated to "notes below" to match. Purely a reorder — nothing about what either control saves or how it behaves changed. Verified via Playwright: DOM order is now checkbox → status line → Save/Request Review → hint → Notes, Save and Request Review both still save correctly in the new position, and the hint text reads correctly in both its Request Review and Cancel Review Request states.

### Added

- Garden Shed desk windows gain a "back" button (10 September 2026), asked directly: opening a document, notice or book from the Notice Board/File Cabinet/Bookshelf always closed that list entirely (their opaque-background, green-bordered look is unchanged, per the request — this is purely a navigation addition), so getting back to it to open something else meant closing the item and re-clicking the hotspot from the shed view, losing any nested File Cabinet folder position in the process. A new ← button now sits next to a desk window's × (in the single-item titlebar, and on the active tab when two or more are open) whenever that window remembers a list it was actually sent to the desk from — clicking it reopens that exact list on top of the desk, leaving the item's own window open underneath rather than closing it, so closing the reopened list again simply reveals it. For the File Cabinet specifically, back restores the *exact* nested folder a document was opened from (walking the same folder-by-folder chain a manual drill-down would build, so the panel's own in-list "← Back" still works correctly from there too), not just the folder-grid root. Items opened some other way — a notice's own linked-document button, a to-do's "View Notice" link, the To-Do List itself — never get a back button, since none of those came from a list in the first place; × still always closes straight back to the plain shed view everywhere, unchanged. Verified via Playwright: a notice sent from the Notice Board, and a document sent from three folders deep in the File Cabinet, both reopen their exact source list via back with the underlying item still open afterward; an item with no list origin gets no back button; in tabbed mode only the active tab carries one. See `Shed/README.md` for the full technical record.

### Fixed

- Garden Shed status/decision chips in the Notice Board, File Cabinet and Bookshelf lists were landing at inconsistent horizontal positions instead of a steady column before the "Desktop" button (10 September 2026), reported directly with a screenshot showing them "all over the place." Root cause was CSS, not markup: `.item-row` used `justify-content:space-between` with an unbounded-width title as its first child, so the row's leftover space was split across every gap between title, chips and the Desktop button — meaning each chip's on-screen position drifted with how long that particular row's title happened to be. Fixed with a single change: `.item-row`'s `justify-content` set to `flex-start` and `.item-row-title` given `flex:1 1 auto` so the title alone absorbs the row's slack. Verified via Playwright across three rows of deliberately varying title length: the Desktop button now lands at the identical x-position on every row, with the chips flush against it.
- Garden Shed login requiring the passphrase to be entered three times most logins that night (10 September 2026), reported directly, with a hard refresh already being tried first each time and not fixing it. Root cause: the lock screen actually had two separate `<form>`/`<input type="password">` pairs in the DOM at once (`#lockFormMobile`/`#lockFormDesktop`, toggled only by CSS `display:none` per breakpoint) — a known trigger for browser password-manager autofill/auto-submit to misbehave when given two live targets on one page, and not something a hard refresh could fix since the duplication was in the page itself, not a cached state. Fixed structurally: collapsed to one shared `<form id="lockForm">` with one `<input id="lockInput">`, repositioned per breakpoint via the same `@media` query that already switches the background art, rather than adding another guard on top of the existing `unlockInFlight`/`autocomplete` mitigations from 9 September. Verified the built page now has exactly one password input inside the lock screen (unrelated password fields exist elsewhere in the app, unchanged), that the single form still positions correctly at both a desktop and mobile viewport, and that unlock still works end-to-end.
- Garden Shed notice status/approval changes weren't reaching an already-open To-Do List tab (10 September 2026), reported directly: approving a notice and changing its shared status from the notice panel left an already-open To-Do List tab still showing "New" with no sign it had been approved. Root cause: the notice panel and the To-Do List tab are two entirely separate desk-window closures, each holding its own copy of the data, and nothing told one about a change made in the other. A new `refreshRelatedDeskWindows` helper is now called after every RPC that changes a to-do's status or a notice's approval/review state — from both directions (the notice panel's Status dropdown and Approved checkbox/Request Review, and the To-Do List row's own status dropdown) — and re-renders any other currently-open window showing the same to-do, live, with no reload or reopen needed. Same request: the To-Do List's own rows now carry the linked notice's own decision badge (✓ Approved / ⚑ Review Requested / Not Yet Approved), the same chip already shown on the Notice Board list row, so both places agree without opening anything. Verified via Playwright in both directions: a status/approval change made in an open notice panel shows up immediately in an already-open To-Do List tab, and a status change made from a To-Do List row shows up immediately in an already-open notice panel for the same notice. See `Shed/README.md` for the full technical record.
- Garden Shed's new black pointing-hand cursor redrawn after direct feedback that the first version ("a rectangle and small protrusion... it almost looks like its giving the finger") didn't read as a hand at all (10 September 2026, same day it shipped). The original was two plain stroked rectangles (a finger, a palm); the replacement is a six-shape silhouette — angled thumb, palm, three staircased folded-finger knuckles, and an extended index finger — combined with a single SVG `<filter>` (`feMorphology` dilate + `feFlood` + `feComposite` + `feMerge`) that produces one clean white halo around the whole hand rather than stroking each shape individually, which would have left ugly seam lines where the fingers meet the palm. This time the replacement was rendered and actually looked at (a light- and dark-background preview screenshot) before it went anywhere near `template.html`, rather than shipped on the strength of the code alone as the first version had been. The plain arrow cursor was untouched. See `Shed/README.md` for the full technical record.
- Garden Shed Notice Board/File Cabinet/Bookshelf lists were only ever fetched once, at unlock, and never again (10 September 2026) — found the hard way: a batch of duplicate test notices created and then deleted earlier the same session (see below) stayed visible in an already-open shed tab because that tab had loaded its list before the delete happened and had no reason to ask again, which read as the cleanup not having worked at all. `openPanel`'s list branch now re-fetches `shed_list_items` every time the Notice Board, File Cabinet or Bookshelf is opened (a brief "Loading…" state, falling back to whatever was already held if the refetch itself fails), and the To-Do List's own fetch now refreshes the same underlying item data alongside its to-dos, so a to-do row's "View Notice" link and its Completed-disabling check always reflect the current approval state too, not just whatever was true at unlock. Verified via Playwright: a notice's decision badge (see below) picks up a change simulated between two opens of the same panel, proving the refetch is real and not just a cache-buster.
- **A test-data mistake, corrected the same day it happened:** while verifying the to-do/notice Completed blocker above, one test notice created via `shed_add_notice` to check the new rule was — it now appears — actually executed 22 times against the live database, almost certainly a network retry on this session's connection resending an already-successful, non-idempotent call. The resulting 22 duplicate "TEST notice for blocker" notices (and their 22 auto-created to-dos) were reported directly from the live Notice Board; a full-table count query (not a check against the one ID originally in mind) found and removed all of them, confirmed with a fresh zero-count check afterward. Recorded here for the honest record, not just fixed quietly.
- Garden Shed File Cabinet titles fixed for six documents showing generic boilerplate text instead of their real title (9 September 2026), reported directly from a screenshot: three "Founder Review Dossiers" rows all read "DRAFT — NOT APPROVED — FOR FOUNDER REVIEW ONLY." Root cause in `shed-doc-sync.mjs`'s `titleFromMarkdown()`: it takes a document's first `#` heading as its title, which breaks for two document templates that reuse the exact same first heading across every instance of that type — an older Founder Review Dossier template that (per FRDS §5.3) preserves this literal status banner verbatim even once approved, and the ARC template's fixed "PIP Mother Information Library — Approved Research Compilation" heading, which turned out to affect all three existing ARCs too, one folder over from what was actually reported. See `Shed/README.md` for the full technical record.

- Garden Shed login flakiness fixed (9 September 2026), reported directly: autofill kept trying the wrong passphrase and unlocking sometimes reverted straight back to the lock screen, usually taking several attempts to get in. Both lock forms now carry a hidden `autocomplete="username"` anchor field ahead of the passphrase input, and the passphrase fields use `autocomplete="new-password"` (respected by browsers, unlike `off`) instead of `off` — addressing the likely cause: two real passphrases saved against one URL with no username field to disambiguate them. The change-passphrase modal's fields got matching semantic `current-password`/`new-password` values. Added an `unlockInFlight` guard in `tryUnlock()` plus `e.stopPropagation()` on both submit handlers, as defense against an autofill auto-submit racing a manual one and slipping through to a native form submission, which — since the forms have no `action` — would reload the page and reset it to the lock screen (nothing is persisted, by design). Verified via Playwright that manual unlock (success and failure) and a rapid double-submit all still behave correctly; the exact real-device autofill interaction itself couldn't be reproduced in this environment, so this targets the best-documented likely causes rather than one proven root cause. - Garden Shed notice review requests fixed to have a way back out (9 September 2026), reported directly against the `Founding_Principles` notice, which had been set to "Review requested" with no way to clear it short of approving outright. Added a `shed_clear_notice_review` RPC that resets a notice's review-request fields without touching its approval or notes, and the notice panel's "Request Review" button now doubles as "Cancel Review Request" whenever a review is currently pending, calling whichever RPC matches the current state.
