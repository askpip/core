# 1. Purpose

Use this Skill to create and edit PIP documents accurately, consistently and efficiently.

Produce work that:

- follows the Founder’s current instruction;
- preserves the intended meaning of source material;
- uses current authoritative PIP information;
- distinguishes proposed wording from approved content;
- records document status truthfully; and
- is ready for Founder review or its intended use.

# 2. Scope

Apply this Skill when asked to:

- draft a new PIP document;
- revise or rewrite an existing document;
- correct spelling, grammar, structure or consistency;
- tighten wording without losing meaning;
- review whether content remains current;
- compare or reconcile related documents;
- convert a document into another textual format;
- prepare repository-ready Markdown;
- update document metadata;
- incorporate Founder-approved decisions; or
- prepare a document for Founder review.

This Skill governs document content and document preparation.

It does not govern:

- repository paths or folder structures;
- retrieval of repository governance files;
- Git status or branch management;
- creating or changing files inside a repository;
- staging, committing, pulling or pushing;
- publication or distribution;
- assigning Founder approval; or
- approving changes to the PIP AI OS.

Use the applicable repository-integration procedure when repository operations are also requested.

# 3. Determine the Requested Action

Before changing content, identify every action in the Founder’s request.

Distinguish between requests to:

- review;
- recommend;
- draft;
- edit;
- reproduce exactly;
- convert;
- create a document;
- create a file;
- replace an existing version; and
- prepare wording for another AI or system.

Do not substitute one action for another.

If the Founder requests a review, do not silently edit the document.

If the Founder requests a draft, do not represent it as an approved document.

If wording must be copied exactly, preserve it exactly unless alteration is separately authorized.

# 4. Establish the Source Material

Identify the material authorized for the task, which may include:

- text supplied by the Founder;
- an attached document;
- an authorized connected source;
- an existing repository document;
- a template;
- related authoritative PIP documents; or
- explicit decisions recorded in the current instruction.

Access every required source before relying upon it.

Do not claim to have accessed a source that was not retrieved during the current task.

When a required source is unavailable:

1. identify the unavailable source;
2. identify the affected work;
3. complete only unaffected work where useful; and
4. request the missing material or Founder direction when necessary.

## 4.1 Naming and Terminology Sources

For document creation, editing, renaming and terminology work:

1. load and apply the PIP System Identity and Naming Standard (SINS-001) at `Standards/PIP_System_Identity_and_Naming_Standard.md`;
2. use the PIP System Terminology Context at `AI/Context/PIP_System_Terminology_Context.md` as the compact operational reference;
3. treat SINS-001 as authoritative where any uncertainty or difference exists; and
4. use approved PIP terminology consistently.

Within each standalone document, define every acronym at its first substantive use by writing the full term followed immediately by the acronym in parentheses.

A title or metadata entry satisfies first use when it contains both the complete term and the acronym.

The first-use requirement does not apply where an acronym appears only within a filename, repository path, URL, domain name, code identifier, configuration value, file extension or another technical context exempted by SINS-001.

Do not introduce an acronym when its shortened form is unlikely to be reused or would reduce clarity.

# 5. Establish Authority and Status

Determine which sources are authoritative within the task.

Apply the PIP authority hierarchy and the Founder’s current instruction.

Treat each source according to its recorded status:

- **Approved:** authoritative within its defined scope unless superseded by higher authority.
- **Active:** currently operative within its defined scope.
- **Founder Review:** proposed content awaiting Founder decision.
- **Draft:** working content open to revision.
- **Source Record:** material retained for reference but not governing current work.
- **Superseded or Archived:** historical material that must not silently replace current content.

Do not treat a newer date, higher version number or polished appearance as proof of authority.

Do not assign or imply Founder approval without explicit authority.

# 6. Plan the Document

Before drafting or editing, establish:

- the document’s purpose;
- its intended audience;
- its required scope;
- its relationship to other documents;
- the required level of detail;
- its current or proposed status; and
- any required format or template.

Use the smallest structure that fully serves the document’s purpose.

Do not add unrelated sections, policies, roles, workflows or commitments.

Where information belongs in another governed document, identify that relationship rather than duplicating it unnecessarily.

# 7. Create or Edit the Content

When creating a new document:

1. use only established information and clearly identified proposals;
2. organize the content around the document’s defined purpose;
3. use PIP’s established terminology;
4. avoid unsupported facts, decisions or commitments;
5. identify uncertainty where it materially affects the document; and
6. assign a truthful draft or review status.

When editing an existing document:

1. preserve wording that the Founder has instructed must remain unchanged;
2. preserve intended meaning unless a change in meaning is authorized;
3. correct spelling, grammar, punctuation and internal inconsistency;
4. improve clarity, flow and structure within the authorized scope;
5. remove unnecessary repetition without deleting distinct meaning;
6. reconcile outdated language with established current decisions;
7. avoid silently introducing new policy or substance; and
8. identify any material change that requires Founder judgment.

Do not make prose longer merely to make it sound formal.

Prefer direct, precise and readable wording.

# 8. Handle Outdated or Conflicting Content

When reviewing older material:

1. compare it with current authoritative sources;
2. identify content that remains valid;
3. identify content that appears outdated, duplicated or superseded;
4. distinguish factual conflict from difference in emphasis;
5. preserve historically useful material when the task requires it; and
6. request Founder direction where reconciliation would require a new decision.

Do not silently resolve a substantive conflict by choosing the wording that appears preferable.

Do not carry obsolete terminology or architecture into a current document merely because it appears in the source.

# 9. Preserve Meaning During Conversion

When converting Google Docs, DOCX, plain text or another textual format:

- preserve the complete substantive content unless editing is authorized;
- preserve heading hierarchy;
- preserve lists, tables, quotations, links and meaningful emphasis;
- preserve metadata accurately;
- remove formatting artifacts that do not carry meaning;
- use valid Markdown when Markdown is requested;
- do not introduce wording changes merely as part of conversion; and
- report any content or formatting that could not be preserved reliably.

Treat conversion and editing as separate actions.

If both are requested, identify and perform both.

# 10. Apply Document Metadata

Use the applicable approved PIP documentation standard or supplied template where available.

Do not invent missing metadata values.

Unless another authoritative format applies, consider the following fields:

- Document Title;
- Document Type;
- Version;
- Status;
- Owner;
- Last Updated;
- Purpose; and
- Related Documents.

Use a date only when supported by the current task or an authoritative record.

Change the version only when authorized or when an applicable standard clearly defines the required change.

Never change a status to **Approved** without explicit Founder authorization.

# 11. Review the Completed Work

Before presenting or saving the result, verify:

- the requested task was completed;
- the document remains within scope;
- Founder instructions were followed;
- required source material was used;
- intended meaning was preserved;
- new proposals are distinguishable from established decisions;
- terminology is consistent;
- acronym first-use, title or metadata satisfaction, technical-context exceptions and unnecessary-acronym requirements comply with SINS-001;
- metadata is accurate;
- heading levels and formatting are coherent;
- spelling and grammar have been checked;
- repetition has been reduced without losing meaning;
- no unsupported approval or authority is implied; and
- no repository action was performed without separate authorization.

Where practical, compare the final document with the source to detect accidental omission.

# 12. Present the Result

Provide the complete revised document when the Founder needs to read or approve it.

Do not provide only a summary when the requested deliverable is the document itself.

State accurately whether the work is:

- a review;
- a proposed revision;
- a draft;
- prepared for Founder review;
- converted but otherwise unchanged; or
- completed under explicit approval.

Briefly identify material changes when that helps Founder review.

Do not claim that a file was created, saved or added to a repository unless that action actually occurred.

# 13. Founder Review and Approval

Keep proposed governance and controlled documents at their truthful draft or review status until the Founders approve them.

When Founder approval is explicitly given:

1. apply only the approval actually granted;
2. preserve the approved wording unless further editing is authorized;
3. update metadata only as authorized or required by an applicable standard; and
4. use the repository-integration procedure for any requested repository changes.

An AI must not approve its own work.

# 14. Completion Report

At completion, report only what is useful for the task, including where applicable:

- the document created or edited;
- its version and status;
- the source material used;
- material changes made;
- unresolved questions or conflicts;
- any unavailable required source;
- whether a file was created or changed; and
- whether further Founder approval is required.

Keep the report proportionate to the work.
